Projects

Four projects, strongest first. Each one starts from the attacker's side and ends with what a defender sees. All are public and run locally.

Nov 2026 · drone command-link detection

MAVLink NIDS demo

Replays drone command-link captures through Suricata and compares the stock rules with 35 custom MAVLink rules.

attacker's view
On a link without message signing, an attacker can flood it, inject a command that appears to come from the ground station, or feed fake GPS positions. The rules match those payload patterns.
defender's view
Rules are written from the protocol specification. Replay is offline, so the demo never sends attack traffic.
result and limit
On the four bundled test captures the stock Emerging Threats rules raised no alerts and the custom rules fired as expected. The captures are synthetic and the rules hard-code the lab addresses. Testing on live traffic is my research project.

Nov 2026 · attacker behaviour

Honeypot network

SSH, Telnet, HTTP and banner sensors that look vulnerable, record what is tried against them and send HMAC-signed events to a collector.

attacker's view
Shows how automated attackers behave: default-credential lists, password spraying and exploit probes for known CVEs in web frameworks and home routers, grouped into campaigns.
defender's view
Sensors have no route out, events are signed with replay protection, and nothing real ever executes.
result and limit
On the built-in 14-day traffic simulator it separates 5 campaigns and flags 1,074 of 1,230 HTTP requests as exploit attempts. It has never been exposed to the internet, so these numbers show the analysis works, not what real attackers do.

Nov 2026 · malware analysis

Malware lab

Static analysis, then detonation in a no-network, read-only Docker sandbox watched with strace. It extracts indicators, maps behaviour to ATT&CK and writes a YARA rule and a report.

attacker's view
Reads what a beacon does: callbacks with jitter on a non-standard port, DNS lookups for command-and-control, persistence.
defender's view
Output is IOCs, ATT&CK techniques and a YARA rule you can deploy, in Markdown, HTML, JSON and STIX 2.1.
result and limit
The safe C2 training specimen scores 24 (benign) on static analysis alone and 94 (malicious) after detonation, which is why the sandbox exists. The lab ships training simulators, not real malware.

Nov 2026 · industrial control systems

ICS attack simulator

A simulated water plant with a PLC, a separate safety system and Modbus/TCP, attacked by eight scenarios mapped to ATT&CK for ICS.

attacker's view
Starts from the attack: raise the caustic setpoint through a remote session, replay the operator's view while closing a valve, rewrite PLC logic, flood Modbus.
defender's view
Seven switchable mitigations. Every scenario is re-run with each one to see what actually helps.
result and limit
405 runs over 5 seeds show no single control covers everything. A range check stops the Oldsmar-style write but not logic changes or replayed telemetry. The physics is simplified and the operator is scripted. Read the sample pentest report on it.

Research project

My final-year project is a purple-team study, so it needs both sides.

in progress · due April 2027

Skyguard Purple Lab: testing Suricata detection of attacks on drone command links

A simulated lab with an ArduPilot drone, a ground station, attacker and relay hosts and a Suricata sensor on an isolated network, with ground-truth logging so every alert can be scored.

  • RQ1How well do default Suricata rules detect flooding, command injection and spoofed position messages, and how fast?
  • RQ2Do custom MAVLink rules improve detection, and by how much?
  • RQ3What is the false-alarm rate of each rule set on normal mission traffic?
  • RQ4Do published results on recorded relay captures (Shadow-GCS dataset) hold in live traffic?

The lab and scoring tools are built and tested. Ethics approval comes before any attack work, and thresholds are fixed before any test run. There are no results yet and I will not claim any until the experiments are done. The custom rules are public in the MAVLink NIDS demo.

How I work

A hunting bat changes its call as it closes in: slow, long calls while searching, faster ones on approach, then a terminal buzz. The spectrogram below is drawn from that pattern, and it is how I run an engagement.

Search
recon and scoping

Read the scope and rules of engagement. Passive first, then active. Map what exists before touching any of it.

Approach
enumeration and analysis

Services, versions, users, paths. Work out what is actually exploitable and why.

Terminal buzz
action and report

Short and precise, only inside scope. Then write it up so someone else can reproduce it and fix it.

Rules I work by

  1. Scope and authorisation come first. No scope, no test.
  2. I only test what I own or have written permission to test: my own lab, Hack The Box and CTFs.
  3. I write down what I did, in an order someone else can follow.
  4. A finding without a fix is half a report.
