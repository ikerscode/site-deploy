ICS attack simulator

A simulated water plant attacked by eight ATT&CK for ICS scenarios.

Attack
Raise the caustic setpoint, replay the operator's view, rewrite PLC logic, flood Modbus.
Defence
Seven switchable mitigations, each re-run against every scenario.
Result
405 runs: no single control covers everything.
Limit
Simplified physics and a scripted operator.
How it works

A PLC with an independent safety system speaks Modbus/TCP to an operator HMI. Each scenario is mapped to ATT&CK for ICS and run against a baseline, then again with each mitigation switched on, over five random seeds.

A range check stops the Oldsmar-style write but not logic changes or replayed telemetry. That is the finding the report is built around.

MAVLink NIDS demo

Custom Suricata rules for a drone command link, compared with the stock rule set.

Attack
Flood the link, inject a command that looks like the ground station's, or feed fake GPS positions.
Defence
35 rules written from the protocol specification. Replay is offline, so no attack traffic is sent.
Result
On four synthetic captures the stock rules stayed silent and the custom rules fired as expected.
Limit
The captures are synthetic and the rules hard-code lab addresses. Live testing is my research project.
How it works

Suricata replays a recorded capture twice, once with the Emerging Threats rules and once with mine, and the page shows which rules fired. On a link without message signing, each of the three attack classes leaves a payload pattern that a rule can match.

Honeypot network

SSH, Telnet, HTTP and banner sensors that look vulnerable and send signed events to a collector.

Attack
Default-credential lists, password spraying and exploit probes for known CVEs, grouped into campaigns.
Defence
Sensors have no route out, and events are HMAC-signed with replay protection.
Result
On a 14-day traffic simulator it separated 5 campaigns and flagged 1,074 of 1,230 HTTP requests.
Limit
Never exposed to the internet, so the numbers show the analysis works, not what real attackers do.
How it works

Each sensor imitates a vulnerable service, records what is tried and ships the events to a collector that stores and analyses them. A simulator generates the traffic, because a honeypot on localhost never sees a real attacker.

Malware lab

Static analysis, then detonation in a no-network Docker sandbox, with indicators, ATT&CK mapping and YARA output.

Attack
Read what a beacon does: jittered callbacks on a non-standard port, DNS lookups, persistence.
Defence
Output is IOCs, ATT&CK techniques and a YARA rule, in Markdown, HTML, JSON and STIX 2.1.
Result
The C2 training specimen scored 24 (benign) statically and 94 (malicious) after detonation.
Limit
The lab ships training simulators, not real malware.
How it works

A sample is hashed, stored read-only and analysed statically. If the format allows, it then runs in a read-only container with no network and dropped capabilities while strace records what it does.

Research project

Skyguard Purple Lab: testing Suricata detection of attacks on drone command links

Final-year project, in progress, due April 2027

A simulated lab with an ArduPilot drone, a ground station, attacker and relay hosts and a Suricata sensor on an isolated network, with ground-truth logging so every alert can be scored.

  • RQ1How well do default Suricata rules detect flooding, command injection and spoofed position messages, and how fast?
  • RQ2Do custom MAVLink rules improve detection, and by how much?
  • RQ3What is the false-alarm rate of each rule set on normal mission traffic?
  • RQ4Do published results on recorded relay captures (Shadow-GCS dataset) hold in live traffic?

The lab and scoring tools are built and tested. Ethics approval comes before any attack work, and thresholds are fixed before any test run. There are no results yet, and I won't claim any until the experiments are done.

Proposal submitted 16 Nov 2026. Now: preparation. Next: pilot and rules (Dec to Jan), then experiments and write-up (Feb to Apr 2027).

How I work

I work like a hunting bat: wide and slow at first, then faster and more precise as I close in.

Search. Read the scope and rules of engagement. Passive first, then active. Map what exists before touching it.

Approach. Services, versions, users, paths. Work out what is exploitable and why.

Terminal buzz. Short and precise, only inside scope. Then write it up so someone else can reproduce and fix it.

Rules I work by

  1. Scope and authorisation come first. No scope, no test.
  2. I only test what I own or have written permission to test: my own lab, Hack The Box and CTFs.
  3. I write down what I did, in an order someone else can follow.
  4. A finding without a fix is half a report.
