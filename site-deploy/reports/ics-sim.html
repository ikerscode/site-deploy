Penetration test report: water-plant ICS simulator

TesterLiam Nichele
Date19 November 2026
Version1.0, public sample
Targetics-sim, commit a1d0787, running on localhost (github.com/ikerscode/ics-sim)

1. Executive summary

I assessed a simulated drinking-water treatment works: a PLC and an independent safety system (SIS) speaking Modbus/TCP, with an operator HMI, an engineering workstation and an office network, laid out on Purdue levels. I ran four attack scenarios against it with no protective controls and found four weaknesses, three rated High and one Medium. Each was fixed by turning on one control and re-running the same scenario with the same random seed.

The main lesson is that no single control covers everything. A range check on the PLC stopped the Oldsmar-style setpoint attack but did nothing against reprogramming or replayed telemetry. A Modbus firewall stopped the flood and the reprogramming but not an attack from an allowed host. The SIS prevented every hazard it has a sensor for, but did it by shutting the outlet, which turned a quality incident into a supply outage.

2. Scope and rules of engagement

  • In scope: the ics-sim simulator at commit a1d0787 on my own machine: PLC-01, SIS-01, HMI-01, EWS-01 and the simulated network zones.
  • Out of scope: everything else. No real network, host or person was tested or scanned.
  • Authorisation: I own and wrote the system, so tester and owner are the same person. A real engagement would have written authorisation from the asset owner before any testing.
  • Method of attack: the scenarios run inside the simulator through its own scenario runner. Source addresses are labels inside the simulation. They never open sockets to anything else.
  • Test window: each run simulates 3 hours with the attack starting at +30 minutes, seed 1. A separate 5-seed matrix (405 runs) is used to check that results are stable.

3. Method

  1. Threat model: I picked eight scenarios mapped to MITRE ATT&CK for ICS. This report covers the four with the clearest remediation lessons.
  2. Baseline: every attack run is compared with a run on the same seed and the same controls with no attack.
  3. Attack run: no mitigations, so the raw weakness is visible.
  4. Rating: CVSS v3.1 base score. I computed the scores with a calculator I checked against published example vectors (9.8, 10.0 and 6.1 all matched). CVSS v3.1 has no safety metric, so the physical consequence is described separately for each finding.
  5. Retest: the same scenario and seed with one mitigation switched on, to verify the fix rather than assume it.

4. Findings

F1. PLC program can be rewritten from an unlisted host 8.2 High

CVSS:3.1/AV:A/AC:L/PR:N/UI:N/S:C/C:N/I:H/A:L · ATT&CK for ICS: T0845, T0843, T0889, T0878

description

The PLC accepts a vendor program upload and download (function code 90) from a host on the supervisory network without checking who is asking. An attacker changes the intake tank hysteresis thresholds to 4.9 m and 5.6 m and suppresses the RAW_HI alarm, so the raw tank overflows with no alarm.

evidence (run 20261119-070422-e67667, no mitigations)

PLC logic tampering: altered hysteresis causes raw tank overflow
mitigations: none -> outcome: hazard occurred
  baseline: availability 100.0% | safety score 100.0 | hazards: none
  attack:   availability 100.0% | safety score 85.0  | hazards: tank_overflow
  attack:   time to hazard: tank_overflow 61.8 min

steps to reproduce

cd ics-sim
.venv/bin/python -m icssim run-scenario logic_tamper --fast

impact

Loss of containment of raw water roughly 62 minutes after the attack, with the alarm that would warn the operator suppressed.

remediation

  • Allow programming function codes only from the engineering workstation (source allowlist at a Modbus firewall).
  • Alert on PLC program change (checksum monitoring), and disable remote programming in normal operation where the PLC supports it.

retest

logic_tamper + firewall   (run 20261119-070643-58e4dc)
mitigations: firewall -> outcome: prevented
  firewall  detected after 0.0 min: Firewall blocked 1 request(s) from 10.10.2.66: source not in allowlist

logic_tamper + detector   (run 20261119-070438-b4c391)
mitigations: detector -> outcome: hazard occurred
  detector  detected after 1.5 min: Anomaly [program_crc]: PLC program CRC changed 41d99cd5 -> 5302ae9b

The firewall prevents it. The detector spots the change after 1.5 minutes but only detects, so the overflow still happens unless someone acts. Across 5 seeds, segmentation and engineering limits did not stop this attack either.

F2. Operator view can be replayed while the process is attacked 8.0 High

CVSS:3.1/AV:A/AC:H/PR:N/UI:N/S:C/C:N/I:H/A:H · ATT&CK for ICS: T0830, T0832, T0815, T0855, T0858, T0831, T0879

description

Telemetry from the PLC to the HMI is not authenticated or sequenced. An attacker in a man-in-the-middle position records normal readings and replays them to the HMI while closing the filter feed and forcing pump P-201 into manual mode. The operator sees a healthy plant while the pump runs dry.

evidence (run 20261119-070419-6e4fa6, no mitigations)

Replay / masking of the HMI view while the process is manipulated (Stuxnet-style)
mitigations: none -> outcome: hazard occurred
  baseline: availability 100.0% | safety score 100.0 | hazards: none
  attack:   availability 39.38%  | safety score 70.0  | hazards: pump_damage, supply_outage
  attack:   time to hazard: supply_outage 42.5 min, pump_damage 43.5 min

steps to reproduce

.venv/bin/python -m icssim run-scenario replay_masking --fast

impact

Pump damage and a supply outage about 43 minutes after the attack, with the attended operator model blind to it for the whole period.

remediation

  • Add a sequence number and an HMAC to telemetry so replayed frames are rejected.
  • Tie detection to a response: an alert with nobody acting on it does not protect the pump.
  • Keep the independent SIS, which does not depend on the HMI view.

retest

replay_masking + integrity   (run 20261119-070435-14b383)
  integrity  detected after 10.0 min: Telemetry integrity: sequence 900 not newer than 1199, replayed data
  outcome: hazard occurred (detection only)

replay_masking + sis   (run 20261119-070645-a47925)
  sis  detected after 39.9 min: SIS TRIP: reservoir low-low level; safe state (dosing off, intake off, outlet closed)
  outcome: prevented (pump damage) | supply_outage still at 41.0 min, availability 38.81%

The integrity check catches the replay the moment it starts, but detection alone does not stop the hazard. The SIS prevents the pump damage and not the outage. Neither one fully closes the finding, which is why the recommendation is a combination plus a response procedure. Note that real PLCs rarely offer telemetry HMAC, so in practice this control would sit in a gateway.

F3. Setpoint writes accepted without range validation 7.7 High

CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:N/I:H/A:N · ATT&CK for ICS: T0822, T0859, T0823, T0836

description

A remote-access session on the HMI PC, protected by a shared password, is taken over and used to write a sodium hydroxide setpoint of 11,100 ppm. The PLC accepts any value, including one far outside the safe range. The scenario follows the publicly reported 2021 Oldsmar incident.

evidence (run 20261119-070416-6fd2ea, no mitigations)

Oldsmar-style caustic setpoint raise through a remote HMI session
mitigations: none -> outcome: hazard occurred
  baseline: quality compliance 100.0% | safety score 100.0 | hazards: none
  attack:   quality compliance 18.82% | safety score 55.0 | hazards: caustic_overdose, ph_out_of_range
  attack:   time to hazard: ph_out_of_range 11.4 min, caustic_overdose 41.4 min
  non-compliant water delivered: 632.1 m3 | max pH 10.88 | max sodium 188.1 mg/L

steps to reproduce

.venv/bin/python -m icssim run-scenario oldsmar --fast

impact

Only 18.8% of the water delivered met quality limits, and pH left its allowed range within 12 minutes. Availability stayed at 100%, which is what makes this attack hard to notice from supply alone.

remediation

  • Enforce engineering limits in the PLC so an out-of-range write is rejected whatever its source.
  • Replace the shared remote-access password with named accounts and multi-factor authentication, and require approval for remote sessions.

retest

oldsmar + eng_limits   (run 20261119-070433-508000)
mitigations: eng_limits -> outcome: prevented
  eng_limits  detected after 1.0 min: Engineering limit rejected write NAOH_SP=11100 ppm (range 0-200)

The write is rejected after 1.0 minute and no hazard occurs. The firewall and segmentation did nothing here (5 of 5 seeds), because the attack arrives from a host that is allowed to talk to the PLC.

F4. Modbus flood from the IT zone exhausts the PLC 6.5 Medium

CVSS:3.1/AV:A/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H · ATT&CK for ICS: T0814, T0815, T0827, T0826

description

The PLC answers Modbus requests from the office network at any rate. A host in the IT zone sends 2,000 requests per second, which starves communications, trips the PLC watchdog and drops the outputs.

evidence (run 20261119-070640-e47ef5, no mitigations)

Modbus flood causing loss of view and loss of control
mitigations: none -> outcome: hazard occurred
  baseline: availability 100.0% | safety score 100.0 | hazards: none
  attack:   availability 16.7%   | safety score 90.0  | hazards: supply_outage
  attack:   time to hazard: supply_outage 1.4 min

steps to reproduce

.venv/bin/python -m icssim run-scenario modbus_dos --fast

impact

Loss of view and control and a supply outage within 84 seconds, with availability down to 16.7%. No contamination, so I rated it Medium, but for a real works an outage is a serious event.

remediation

  • Segment the IT zone so it cannot reach the PLC at all.
  • Put a source allowlist and a rate limit in front of the PLC.

retest

modbus_dos + firewall   (run 20261119-070441-f82361)
mitigations: firewall -> outcome: prevented
  firewall  detected after 0.0 min: Firewall blocked 1000 request(s) from 192.168.10.37: source not in allowlist

Segmentation also prevents it. The SIS cannot help, because the attack never touches the process it protects.

5. What held up

  • 45 baseline runs (no attack, every control column, 5 seeds) raised no false alerts and no hazards.
  • The SIS prevented every hazard it has a sensor for in the scenarios above, though sometimes at the cost of availability (22% to 58% in those runs).
  • Results were stable across seeds: no cell of the 405-run matrix changed outcome between seeds. The seed only varies process and sensor noise, so this shows robustness to noise, not to a different operator.

6. Limitations

  • This is a simulator with simplified physics and a scripted operator. Times to hazard show mechanisms and relative differences, not predictions for a real works.
  • The attacks run inside the simulator through its scenario runner. I did not write novel exploits, and nothing here is a claim about real PLCs or networks.
  • I rated the findings myself. A second scorer would probably disagree on some metrics, particularly attack complexity on F2.
  • Only one mitigation was switched on per retest. Real remediation is layered, and the 405-run matrix in the repository shows the combinations.
